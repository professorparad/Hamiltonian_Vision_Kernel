# Main_new: HVK1D with a working Hamiltonian objective

This is a copy of `Main/` (the original HVK1D implementation) with two changes to the
learned Heisenberg energy term, made to address a reviewer finding: the paper's own
ablation (Table X, `latex_outputs/paper_latex/supplementary_study.tex`) shows that
removing the energy loss *improves* reconstruction (32.24 -> 33.30 dB), meaning the
"Hamiltonian"/"physics-informed" framing was not earning its keep as a performance
motivation.

## Diagnosis

In the original model (`Main/src/quantum/quantum_model.py`), the learned couplings
`Jx, Jy, Jz` are free, unconstrained parameters that feed **only** the energy loss term
(`energy = sum(Jz*ZZ) + sum(Jx*XX) + sum(Jy*YY)`) — they never reach the decoder via the
observable vector. With a plain linear energy loss (`torch.mean(energies)`), the
optimizer can trivially drive these couplings to unbounded magnitude to cheaply minimize
the energy term, independent of reconstruction quality — actively competing with the
reconstruction gradient on the shared circuit weights (`self.weights`, which do affect
both the observables and the energy) for no benefit.

## Fix (two changes, both needed together)

1. **Bounded couplings** (`src/quantum/quantum_model.py`): `Jx, Jy, Jz` are now read-only
   properties returning `torch.tanh(Jx_raw)` etc. of underlying unconstrained parameters
   `Jx_raw, Jy_raw, Jz_raw` — bounded to `(-1, 1)`, so they can no longer grow without
   limit. Everywhere else that reads `model.Jz` (checkpoint saving, R_ES tracking, etc.)
   is unaffected since the property still returns a plain tensor.
2. **Bounded energy loss** (`src/training/training.py`): default `energy_loss_mode`
   changed from `"linear"` to `"positive"` (`torch.mean(energies.square())`) — already
   implemented in the original codebase but never tested in Table X. Squaring means
   driving energy to *either* extreme is penalized, not just one direction, removing the
   other half of the same underlying pathology.

## IMPORTANT: a reproducibility gap in Table X, found while validating this fix

Before trusting any comparison against Table X's published numbers, re-running the
*unmodified* Table X configurations (legacy linear energy, no-energy-loss, contrastive —
none of which this folder touches) at the documented protocol (Monalisa, 256x256/patch=64,
`model_variant=standard`, 200 steps — the `Main/src/config/training_config.json` default,
confirmed via the installed package versions matching the paper's documented environment
exactly: PennyLane 0.42.3, PyTorch 2.6.0+cu124) reproduces PSNR values 6-12 dB **higher**
than published, across every variant tested, not just the new one:

| Config | Table X (published) | Fresh reproduction, 2026-07-28 (seed 42, 200 steps) |
|---|---|---|
| Legacy signed energy | 32.24 dB | 38.63 dB |
| No energy loss | 33.30 dB | 44.56 dB |
| Contrastive | 32.84 dB | 42.92 dB |

An earlier attempt at 120 steps gave a *worse* legacy-energy number (30.67 dB) than
published — so the gap isn't simply "more steps than intended." The likely explanation:
Table X was generated by a different script than `Main/src/training/training.py`'s
default CLI path — commit history references
`experiments/quantum_contribution/run_scripts/run_hamiltonian_core.sh` and an
`INTERPRETATION.md`, but that whole directory is gitignored
(`experiments/quantum_contribution/`) and the actual files are gone from the working
tree; `git show`/`git cat-file` confirm they were never actually committed (the commit
*messages* list them, generated from an uncommitted `git status`, but the blobs don't
exist in any tree). The original protocol could not be recovered.

**Decision (confirmed with project owner, 2026-07-28)**: rather than block on
recovering the lost protocol, use this fresh, self-consistent, same-environment
reproduction as the new baseline going forward, with this gap disclosed explicitly
wherever these numbers are used (paper text, `q1_revision/04_hamiltonian_objective/`).
Do not silently overwrite Table X's numbers without this note.

All at seed 42. Honest read: at this single seed, `positive` energy mode (bounded or
not) **ties with removing the energy loss entirely** (44.56-44.69 dB) — it no longer
*hurts* reconstruction the way the legacy linear mode does (which trails by ~6 dB), but
it does not yet clearly *beat* "no energy loss" either. That's a more modest finding
than an initial single-seed reading suggested. The bounded-coupling change specifically
does not appear to add anything on top of `positive` mode by itself at this seed
(44.56 vs 44.69 dB, within run-to-run noise).

**Multi-seed check in progress** (seeds 43, 44 for `no_energy_loss` vs this folder's

# Main HVK1D Pipeline (original docs below, still accurate for this copy)

`Main/` contains the primary HVK1D reconstruction pipeline. This is the version
used for the standard chain model and the U(1)-symmetric chain model.

The entry point is:

```powershell
python Main\main.py --device auto
```

## What Happens In A Run

The training script:

1. Loads a grayscale image, usually `Main/data/monalisa.jpg`.
2. Splits the image into square patches.
3. Extracts MPS-style features from each patch.
4. Builds sinusoidal positional encodings for patch locations.
5. Sends features and positions into a PennyLane variational circuit.
6. Computes observables and a Hamiltonian energy term.
7. Trains a patch decoder with reconstruction loss plus energy regularization.
8. Stitches reconstructed patches back into an image.
9. Optionally saves plots, GIFs, order-parameter curves, and metrics.

## Variants

`Main/main.py` supports:

- `standard`: learnable `Jx`, `Jy`, and `Jz` couplings.
- `symmetric`: U(1)-symmetric coupling structure, `J * ZZ + K * (XX + YY)`.
- `both`: runs standard and symmetric side by side and writes comparison output.

Example:

```powershell
python Main\main.py --model-variant both --steps 120 --device auto
```

## Source Layout

- `main.py`: CLI wrapper and variant comparison logic.
- `src/training/`: dataset construction, training loop, phase media, and order
  parameter tracking.
- `src/quantum/`: PennyLane circuits and HVK quantum model classes.
- `src/tensornetworks/`: MPS feature extraction and reconstruction helpers.
- `src/preprocessing/`: image loading, patch extraction, and positional encoding.
- `src/decoder/`: neural patch decoder.
- `src/reconstruction/`: patch stitching and seam blending.
- `src/visualization/`: plotting helpers.
- `src/config/training_config.json`: default run configuration.

## Device Behavior

Use `--device auto` unless you are debugging.

The Torch parts can use CUDA when available. The PennyLane quantum simulator
uses CUDA only when `lightning.gpu` is installed. Otherwise the code prefers
`lightning.qubit` on CPU, then falls back to `default.qubit`.

This avoids the common failure mode where Torch tensors are on CUDA but the
PennyLane simulator is still CPU-only.

## Outputs

Default outputs go to:

```text
Main/outputs/training_analysis/
```

Typical files include reconstructions, training curves, order-parameter plots,
phase-transition GIFs, and JSON summaries.

Use `--no-save` for quick debugging:

```powershell
python Main\main.py --steps 1 --no-save --model-variant standard --device auto
```
